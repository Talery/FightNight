# Release checklist и rollback

Документ рассчитан на неподписанный portable-выпуск и offline-first PWA. Пункты production выполняются только после закрытой beta и при наличии владельца инфраструктуры.

## 1. Зафиксировать кандидата

- записать версию приложения, `SAVE_VERSION` и `DAILY_RULESET_VERSION`;
- проверить, что `RELEASE_CONTRACT.json` имеет статус `frozen-rc` и совпадает с package/save/RunSummary/daily-константами;
- убедиться, что в рабочем дереве нет случайных секретов, `.env` и персональных beta-данных;
- выполнить `npm ci`, `npm run check`, `npm run simulate` и Deno check Edge Function;
- сохранить итог release audit: число тестов, размер `dist`, крупнейший JS chunk и результат 1 000 прогонов;
- не менять баланс, сетевой контракт и формат сохранения после этого пункта без нового кандидата.

## 2. Данные и совместимость

- прогнать синтетическую матрицу миграций v1–v18;
- прогнать анонимизированные копии реальных beta-сохранений, когда они появятся;
- проверить экспорт текущего сохранения, импорт на чистом профиле и восстановление из backup;
- до миграции production сделать независимый экспорт схемы и данных backend средствами владельца проекта;
- сохранить точную копию применяемого `supabase/schema.sql` рядом с release notes;
- любые необратимые SQL-операции требуют отдельного плана восстановления и ручного подтверждения владельца данных.

## 3. Web/PWA

- развернуть кандидата на отдельном preview URL;
- проверить HTTPS, manifest, иконки, установку и первый запуск;
- открыть установленную PWA без сети и завершить обычный бой;
- обновить предыдущую установленную версию, убедиться, что service worker загрузил новый кандидат и сохранение мигрировало;
- проверить 360, 390, 768, 1280 и 1920 px, клавиатуру, reduced motion и крупный текст;
- только после smoke переключить production на неизменённый проверенный артефакт.

## 4. Verified daily

- сверить серверный и клиентский `DAILY_RULESET_VERSION`;
- проверить общий seed на двух чистых клиентах;
- отправить валидный журнал, повтор того же журнала, подменённый score и слишком большой журнал;
- проверить rate limit, pending-очередь после перезапуска и повторную отправку после восстановления сети;
- убедиться, что обычная кампания работает при полном отключении backend;
- проверить, что публичные таблицы не позволяют браузеру вставлять verified-результаты.

## 5. Windows portable

- собрать архив уникальной версией: `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/package-windows.ps1 -Version <version>`;
- распаковать его в новую папку и запустить `PLAY.cmd`, не используя файлы исходного дерева;
- получить HTTP 200 для `/` и production JS entry;
- проверить обычный бой без интернета и сохранение после перезапуска;
- опубликовать размер и SHA-256 архива;
- явно указать, что `PLAY.cmd` и архив не подписаны цифровой подписью.

## 6. Rollback

Откат web выполняется переключением хостинга на последний известный хороший неизменённый артефакт. Нельзя откатывать клиент ниже минимальной версии, способной прочитать уже созданные сохранения, без отдельного forward-compatible патча.

Если неисправен только verified daily, сначала отключить клиентские `VITE_SUPABASE_*` или endpoint функции и оставить одиночную игру в локальном режиме. Уже подтверждённые строки не удалять; спорный сезон пометить отдельно после анализа.

Если миграция backend повредила данные, остановить запись, сохранить текущее аварийное состояние и восстановить заранее созданную резервную копию в отдельный проект. Переключение production выполняет владелец инфраструктуры только после сравнения количества строк и контрольного replay.

Windows-архивы неизменяемы: ошибочный архив отзывается, публикуется новый номер кандидата и новая SHA-256. Старый файл не перезаписывается.

## 7. Go/no-go

Выпуск запрещён при потере сохранения, softlock, неработающей offline-кампании, возможности записать forged verified score, отсутствии backup production-схемы или неизвестном происхождении финального артефакта. Внешние beta-метрики и production smoke нельзя заменять локальными тестами.
